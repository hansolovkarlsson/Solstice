## Functions — implemented, tested, and a real bug caught and fixed

**Design**: reused the existing local-variable machinery entirely rather than adding new AST nodes. A function reserves one hidden extra frame slot (`return_slot`) beyond its real parameters/locals; assigning to the function's own name inside its body (`FuncName := expr;`) is recognized by the parser as targeting that slot via the ordinary `NODE_LOCAL_ASSIGN` mechanism. At the end of the function's body, `LOAD_LOCAL <return_slot>` pushes the result right before `RET` — the same "leave the result on the operand stack" convention already proven at the VM level two sessions ago.

**New opcode**: `OP_POP` — needed because a function called *as a statement* (its value discarded) still pushes a return value that nothing consumes; without popping it, the operand stack would silently corrupt for everything after it.

**A real, serious bug found and fixed**: `NODE_CALL`'s codegen unconditionally propagated `->next`, which is correct when a call is a *statement* (continuing the enclosing statement chain) but wrong when it's an *expression* used as a non-last argument in a list (`write(fib(i), ' ')`, or as a non-last argument to another call) — in that case `->next` belongs to the *enclosing* argument-list loop, which already walks it. The bug manifested as `write(fib(i), ' ')` silently producing all zeros for a Fibonacci sequence — caught by actually running the test rather than trusting the code, then confirmed and root-caused via `desole`. Fixed by using the same `node->op == TOKEN_PROCEDURE` marker already distinguishing statement/expression context to also gate `->next` propagation. `NODE_CALL` is structurally the *only* node type that could have this bug (every pure-expression node type never touches `->next` at all), so this was a complete fix, not a partial patch.
