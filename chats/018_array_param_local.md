
Array Parameters and Array Locals

# Prompt

So next task is to implement array parameters and array locals

# Response

This is a bigger design problem than it might look, so let me work through it before writing code.

**The core tension**: scalar locals get fresh, isolated storage on every call (that's what made recursion with parameters work correctly). Arrays don't fit that model as easily — `vm_frame_stack` holds one `int` per slot, but an array needs *contiguous* storage sized to its bounds, and the existing array machinery (`vm_array_mem`, bounds-checked via a `sym_table` lookup) was built entirely around arrays being *global*, allocated once, at a fixed offset known at compile time.

**Two genuinely different cases, and I want to treat them differently:**

1. **A procedure's own `var`-declared array** (not a parameter) — I'm going to reuse the *existing* global array machinery outright, via a hidden, compiler-generated name (same trick already used for `for`'s hidden loop-bound variable). This means **zero new opcodes** for this case. The honest trade-off: like a real global, it's allocated *once* for the whole program and shared across every call to that procedure — **not** freshly isolated per call the way scalar locals are. For a recursive procedure that needs each call to have its own independent array, this won't be right, and I'll document that clearly. For the much more common non-recursive "temporary working array inside a procedure" case, it's exactly correct.

2. **Array parameters** — these are the genuinely new mechanism. I'll pass them **by reference, always to an existing array** (a global, or the caller's own array parameter/local) — never by copying the whole array's contents. Concretely: the caller must pass a bare array name (not an expression) whose declared bounds and element type exactly match the parameter; what actually gets passed at runtime is that array's `sym_table` index, sitting in an ordinary parameter slot. This does need two new opcodes (`LOAD_IDX_DYN`/`STORE_IDX_DYN`) — the existing `LOAD_IDX`/`STORE_IDX` bake *which* array into the instruction itself as a compile-time constant, which can't work here since different calls can pass different arrays; the new ones read that at runtime instead, off the operand stack.
